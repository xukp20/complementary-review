# Complementary Review

Claude 把握方向，Codex 落实细节，双方各自针对对方的常见问题做审查。

这个 skill 按 Claude 和 Codex 各自的长处分配计划、审查和验证工作。同一份 skill 可以同时装在两边，各自读自己那一侧的说明。工作怎么在两边之间传递，这个 skill 不管：可以由用户转交文档，也可以在用户要求时由一方直接给另一方发消息。

## 为什么

两边出错的方式不一样：

- **Claude** 擅长开放式思考、抓核心问题、提出方向、判断先后。容易出的问题是：只读了一部分就下事实结论，粗略估计说得过于肯定，计划方向对但细节不足。
- **Codex** 读代码和记录精确，执行可靠、周全。容易出的问题是：死板地照计划执行，加入没有具体风险支撑的限制和流程，在非核心的方向上反复迭代。

所以各自在长处上主导，审查对方时重点看对方的常见问题，在对方擅长的部分接受对方的判断：
- Claude 审查方向和阻力；
- Codex 核对事实和可行性，并把方向细化成可执行的步骤。

## 带来的变化

- **Claude 审 Codex 的计划**：看是否抓住核心问题，有没有注定拿不到结果的实验、没必要的限制、卡住的方向，以及遗漏的方向。不纠缠措辞和命令细节。
- **Codex 审 Claude 的计划**：核对事实，指出已有能力和真实接口，给出可行步骤。不重开已经定下的方向，也不新增门禁。
- 任何一方写的计划和重要结论，在推动较大的工作之前，先让对方看一遍。已认可计划内的常规实现，不需要来回传递。
- 每次交接都写清两件事：希望对方核对什么，哪些点需要用户决定。

skill 不规定目录、文件名或文档格式，不增加调度器、审批门或必交报告，也不授权执行。

## 两种交互方式

- **各自独立的文档**：适合独立评估、没有原始目标文档的审查，或者需要把双方立场分开保留的情况。
- **共享同一份文档**：适合收敛到一份计划。各自的修改和异议要能看出是谁写的，不悄悄改动对方的论证。

怎么送达是另一回事：由用户转交，或者用户让一方通过本机已有的通道直接发消息给另一方都可以，审查原则不变。

## 安装与使用

安装命令见[英文说明](README.md#install)，把 `skills/complementary-review` 分别链接到 Claude Code 和 Codex 的 skills 目录即可。

示例：

> （Claude Code）/complementary-review 审查 Codex 在 <路径> 的计划，重点看方向、注定拿不到结果的实验和没必要的限制，标出需要我决定的点。

> （Codex）使用 $complementary-review，把 Claude 在 <路径> 的计划细化成可执行步骤，按源码核对其中的事实，保持原方向。
